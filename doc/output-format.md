# 生成文件的格式

这份文档是**契约**：生成器写出来的东西长什么样，消费端该按什么顺序读回去。
分三块——注释块、常量、解码步骤。

## 注释块

注释块按**管线执行的顺序**逐行列出，从上往下读就是输入变成数组的过程。
每一步只在真的执行了才出现；不压缩也不加密时，只剩一行
`generated by bin2source - do not edit`。

```
zstd    : frame, level 19
AES256CBC (PKCS#7)
iv      : 4f768bc52df0bfd6fb08b94754f7dfb3  (array[0:16])
key     : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90

Constants:
  greet               the array: zstd output, encrypted with AES256CBC, led by its 16 byte IV
  greet_len           bytes the array holds
  greet_raw_len       bytes the input file held, before compressing
  greet_sha256        digest of the input file, before compressing or encrypting
  greet_zstd_sha256   digest of the zstd output, after compressing, before encrypting
  greet_array_sha256  digest of the array's own bytes, the IV included
```

| 行 | 什么时候出现 | 说明 |
| --- | --- | --- |
| `<codec> : <wire>, level N` | 给了 `--compress` | 算法名、输出形态、级别 |
| `AES256CBC (PKCS#7)` | 给了 `-cbc` | 用的哪种加密，CBC 带填充标注 |
| `iv` | 给了 `-ctr` / `-cbc` | 16 字节 IV，小写 hex，括号里说明 IV 在哪 |
| `key` | 给了 `-ctr` / `-cbc` | 32 字节密钥，小写 hex |
| `Constants:` 整段 | 给了 `--compress` 或 `-ctr` / `-cbc` | 逐个说明下面每个常量存的是什么，见下文 |

`<wire>` 那个词是**必须看的**，而且**它是算法自己声明的，不是生成器统一印的**：

| 行 | 形态 | 含义 | 消费端对应 |
| --- | --- | --- | --- |
| `deflate : raw, level 9` | `raw` | RFC 1951 裸流，**没有** zlib / gzip 头 | `inflateInit2(-15)` / `flate.NewReader` / `zlib.decompressobj(-15)` |
| `zstd : frame, level 19` | `frame` | RFC 8478 frame，Zstandard 只有这一种形态 | `ZSTD_decompress` / `zstandard.ZstdDecompressor` / `flate2` 之外单独引 |

`deflate` 写 `raw` 是有信息量的：光看算法名判断不出外面有没有套头，而两种解码器
的参数完全不同。反过来，`zstd` 写 `frame` 是在说"这里没有裸流可选，别去找了"——
Zstandard 只有 frame 一种线上形态，如果这里印成 `raw` 就会把消费端引向一个不存在
的解码选项。

标签都补到 8 字符宽，所以 `:` 在同一列上对齐（`deflate` 正好 8 个字符，`zstd`
补 4 个空格）。

`iv` 行的括号有两种取值：

- `(array[0:16])` —— IV 就是数组的前 16 字节，密文从第 16 字节开始
- `(comment only)` —— 数组里只有密文，IV 得自己从这行注释里抄进代码

注释里**不写文件大小**，也不写任何摘要值。长度由常量表达，摘要也是常量。
注释只描述"用了什么参数"，参数之外的东西一律以代码常量为准，这样两者不会
互相矛盾。

> IV 是每次运行随机生成的，所以同一份输入加密两次，产出的源码完全不同。
> 这是正确行为，不是 bug。压缩本身不带随机量：只给 `--compress` 的输出是可复现的。

### `Constants:` 段

只要数组不是输入文件的原样拷贝，下面的常量名就**不再自解释**了，注释会把每个
名字对应的阶段写清楚：

| 名字 | 存的是什么 |
| --- | --- |
| `greet` | 数组本身：按注释上半段描述的那样压缩、加密后的字节 |
| `greet_len` | 数组有多少字节 |
| `greet_raw_len` | 输入文件原来有多少字节（只压缩时出现） |
| `greet_sha256` | **输入文件**的摘要，压缩和加密之前 |
| `greet_zstd_sha256` | 压缩输出的摘要，加密之前（`<codec>_sha256`） |
| `greet_array_sha256` | 数组自己那些字节的摘要，`-iv 1` 时含 IV |

这段存在的理由是一个真实的误读：`greet_sha256` 看着像"名叫 greet 的数组的摘要"，
但它不是，数组的摘要是 `greet_array_sha256`。不带后缀的那个永远是**输入文件**，
而这一点从紧挨着的同名数组身上推不出来，只能靠注释说。

描述会跟着管线走：只压缩时不提"加密"，只在压缩+加密时才说"before compressing or
encrypting"。没跑过的步骤不出现在描述里。

不压缩也不加密时**不输出**这一段：那时数组就是文件，每个常量只有一种可能的含义，
加了反而多余。

各语言用各自的命名，`Constants:` 段里的名字跟着变：

| 语言 | 这一段里的样子 |
| --- | --- |
| C / C++ | `greet_zstd_sha256` |
| Go | `GreetZstdSha256` |
| Rust | `GREET_ZSTD_SHA256` |
| Python | `GREET_ZSTD_SHA256` |

## 长度常量

数组长度之外，压缩时还会多一个**原始长度**常量。

| 常量 | 含义 | 什么时候出现 |
| --- | --- | --- |
| `data_len` | 数组里有多少字节（压缩 + 加密后的结果） | 永远 |
| `data_raw_len` | 输入文件有多少字节（压缩之前） | 给了 `--compress` |

`raw_len` 是**唯一无法从数组推导出来的数字**：裸 DEFLATE 流不带原始长度
（那是 gzip 的 ISIZE 字段）。C 和 C++ 的消费端必须先分配好缓冲区才能 inflate，
没有这个值就只能靠失败重试来扩容。Go / Rust / Python 可以流式解，但拿它当
"解压结果长度对不对"的第一道检查同样有价值。

不压缩时不需要它：那时原始长度要么等于数组长度，要么由填充规则唯一确定。

各语言的拼写（数组标识符为 `data` 时）：

| 语言 | 数组长度 | 原始长度 |
| --- | --- | --- |
| C | `static const unsigned int data_len = 48;` | `static const unsigned int data_raw_len = 104;` |
| C++ | `static constexpr unsigned int data_len = 48;` | `static constexpr unsigned int data_raw_len = 104;` |
| Go | `var DataLen = len(Data)` | `const DataRawLen = 104` |
| Rust | `pub const DATA_LEN: usize = DATA.len();` | `pub const DATA_RAW_LEN: usize = 104;` |
| Python | `DATA_LEN = len(DATA)` | `DATA_RAW_LEN = 104` |

Go 的数组长度用 `var`（`len()` 不是常量表达式），原始长度用 `const`（是字面量）；
Rust 的 `const` 必须写类型，所以那行比较长。

给了 `-b64` 时没有数组可测长度，`DataLen` / `DATA_LEN` 也改成字面量
（`const DataLen = 48` / `pub const DATA_LEN: usize = 48;`）；C / C++ / Python
本来就不受影响。

## 三级 SHA-256

从输入文件到数组，字节被改了三道，于是**每一道边界都有一个摘要常量**。
它的用途是：回读失败时能定位到是哪一步出的问题，而不是只知道"对不上"。

| 常量 | 覆盖的字节 | 消费者拿它做什么 |
| --- | --- | --- |
| `data_sha256` | **输入文件**（压缩、加密之前） | 最终比对，确认拿到的和当初塞进去的一致 |
| `data_<codec>_sha256` | 压缩输出（加密之前） | 解密后比对，确认密钥和 IV 没错 |
| `data_array_sha256` | **数组里的字面字节**（`-iv 1` 时含前 16 字节 IV） | 不用密钥就能比对，确认源码里的数组没被改坏 |

中间的常量名字里带着算法名，`--compress deflate` 是 `data_deflate_sha256`，
`--compress zstd` 是 `data_zstd_sha256`。这样两种算法的摘要不会互相顶替，
将来加第三个算法也不用改命名规则。

三个常量的出现规则由参数决定，不是由数量决定，所以可以放心依赖：

| 调用 | `data_sha256` | `data_<codec>_sha256` | `data_array_sha256` |
| --- | --- | --- | --- |
| 都不给（现状） | ✅ | — | — |
| `--compress deflate` | ✅ | ✅ `deflate` | — |
| `--compress zstd` | ✅ | ✅ `zstd` | — |
| 只有 `-ctr` / `-cbc` | ✅ | — | ✅ |
| `--compress zstd -cbc` | ✅ | ✅ `zstd` | ✅ |

也就是说中间那个摘要出现**当且仅当**给了 `--compress`，`array_sha256` 出现
**当且仅当**给了 `-ctr` 或 `-cbc`。这样纯压缩时不会出现两个内容完全相同的常量：
那时数组就是压缩输出，`<codec>_sha256` 已经覆盖了它。

### `array_sha256` 为什么按"整个数组"算

`-iv 1` 时数组是 `[IV(16) | 密文]`。这个摘要覆盖**数组里那串字面量的全部字节**，
包含 IV，而不是只算密文：

- 这样比对时直接把数组丢进哈希函数就行，**不需要先切掉 IV**——切片那一步本身
  又是一个可能切错的地方；
- 它因此成为**唯一不需要密钥的完整性检查**。手改过数组、传输时换行符被转换、
  文件被截断，都能在拿到密钥之前发现。

代价是它不能用来单独验证密文，因为它把 IV 也算进去了——这是有意的取舍。

### 各语言的常量名

数组标识符为 `greet` 时：

| 语言 | 输入文件 | 压缩输出 | 数组 |
| --- | --- | --- | --- |
| C | `greet_sha256` | `greet_deflate_sha256` / `greet_zstd_sha256` | `greet_array_sha256` |
| C++ | `greet_sha256` | `greet_deflate_sha256` / `greet_zstd_sha256` | `greet_array_sha256` |
| Go | `GreetSha256` | `GreetDeflateSha256` / `GreetZstdSha256` | `GreetArraySha256` |
| Rust | `GREET_SHA256` | `GREET_DEFLATE_SHA256` / `GREET_ZSTD_SHA256` | `GREET_ARRAY_SHA256` |
| Python | `GREET_SHA256` | `GREET_DEFLATE_SHA256` / `GREET_ZSTD_SHA256` | `GREET_ARRAY_SHA256` |

中间那一列用哪个名字，取决于 `--compress` 给的是哪个算法；同一份文件里只会
出现其中一个。

值的类型和写法：

| 语言 | 类型 |
| --- | --- |
| C | `static const char []` |
| C++ | `static constexpr const char []` |
| Go | 无类型字符串常量 |
| Rust | `&str` |
| Python | `str` |

都是 64 个字符的**小写** hex，可以直接和 `sha256sum` / `Get-FileHash` /
`hashlib` 打印出来的字符串比对。

C / C++ 和 Python 会把字面量折进括号里，Go 和 Rust 是单行。
Rust 的 `const` 必须写类型，所以那几行比较长。

## 各语言的形态

下面是同一个 5 字节文件 `\x01\x02\x03\x04\x05` 用 `-cbc` 生成的结果，
**不带压缩**。（五份的 IV 不一样，因为每次运行都随机取 IV。）

### C —— `data.h`

```c
/*
 * generated by bin2source - do not edit
 * AES256CBC (PKCS#7)
 * iv      : 40bf5d9047be1d71656bb5734b53d0af  (array[0:16])
 * key     : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90
 */
#ifndef DATA_H
#define DATA_H

static const unsigned char data[] = {
	0x40, 0xbf, 0x5d, 0x90, 0x47, 0xbe, 0x1d, 0x71, 0x65, 0x6b, 0xb5, 0x73, 0x4b, 0x53, 0xd0, 0xaf, 0x3c, 0x08, 0xe6, 0x93, 0xa8, 0x57, 0x98, 0xb5, 0xdc, 0xf1, 0x4a, 0xba, 0xbe, 0xae, 0xad, 0x1b,
};

static const unsigned int data_len = 32;

static const char data_sha256[] = (
	"74f81fe167d99b4cb41d6d0ccda82278caee9f3e2f25d5e5a3936ff3dcec60d0"
);

static const char data_array_sha256[] = (
	"ce3bd3d206fa4d1eedb6c740bab776bf20bea36359318c91b0defa2cb47a766a"
);

#endif /* DATA_H */
```

单文件头文件，`static` 给数组内部链接：被多个翻译单元 include 都能编过，
代价是每个单元各有一份私有副本。不想重复就把它放进单独一个 `.c`。

### C++ —— `data.hpp`

和 C 完全同构，只有扩展名、include guard 后缀和 `constexpr` 三处不同：

```cpp
static constexpr unsigned int data_len = 32;
```

### Go —— `data.go`

```go

}
```

第一行是 Go 工具链用来识别生成文件的固定写法，`gopls` 和 lint 会因此跳过它。
写成 `[]byte` 变量而不是字符串常量，是为了能直接丢给 `os.WriteFile`。

### Rust —— `data.rs`

```rust
// generated by bin2source - do not edit
// AES256CBC (PKCS#7)
// iv      : 6794f606bc3c7d45b1b18ac9ba462886  (array[0:16])
// key     : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90

pub const DATA: [u8; 32] = [
	0x67, 0x94, 0xf6, 0x06, 0xbc, 0x3c, 0x7d, 0x45, 0xb1, 0xb1, 0x8a, 0xc9, 0xba, 0x46, 0x28, 0x86, 0xb9, 0x7c, 0x2f, 0x2a, 0xa0, 0xda, 0x3d, 0x85, 0x52, 0x83, 0x9b, 0xdc, 0x05, 0x19, 0xd2, 0x1b,
];

pub const DATA_LEN: usize = DATA.len();

pub const DATA_SHA256: &str = "74f81fe167d99b4cb41d6d0ccda82278caee9f3e2f25d5e5a3936ff3dcec60d0";

pub const DATA_ARRAY_SHA256: &str = "969329eb3a5370c65e41b6f21b9ea4345a76a48680a010c6e9a675527b63e75b";
```

Rust 的数组长度必须写进类型 `[u8; 32]`，所以这个数字会出现两次——类型里一次，
`DATA_LEN` 从 `.len()` 推导一次。`-pkg` 会在外面包一层 `pub mod`。

> **Rust 使用注意：必须传引用。**
>
> ```rust
> std::fs::write("out.bin", &DATA)?;   // 对
> std::fs::write("out.bin", DATA)?;    // 超过 1 MB 就栈溢出崩溃
> ```
>
> `[u8; N]` 是 `Copy` 类型，按值传递会整份 `memcpy` 到栈上，而 Windows 主线程栈
> 默认只有 **1 MB**（Linux 是 8 MB）。实测：1 MB 的数组按值传还能跑，2 MB 就
> `thread 'main' has overflowed its stack`。也就是说**任何超过 1 MB 的资源在
> Windows 上按值用都会崩**，图片、字体基本都会中招。
>
> `&DATA` 是引用，不拷贝，没有这个问题。这也是 `include_bytes!` 返回
> `&'static [u8; N]` 而不是数组本身的原因。
>
> 另外 `const` 在每个使用点都会被内联，不过 LLVM 会合并相同常量，实测多处引用
> 二进制不会变大。

### Python —— `data.py`

```python
# generated by bin2source - do not edit
# AES256CBC (PKCS#7)
# iv      : 5cf99dc7811cb8cdc3f2cc7976afd116  (array[0:16])
# key     : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90

DATA = bytes.fromhex(
    "5cf99dc7811cb8cdc3f2cc7976afd116e8925d2be3dd72fd9c4804ea7e2bda2f"
)

DATA_LEN = len(DATA)

DATA_SHA256 = (
    "74f81fe167d99b4cb41d6d0ccda82278caee9f3e2f25d5e5a3936ff3dcec60d0"
)

DATA_ARRAY_SHA256 = (
    "0428c1925ea375c7017489e3a9d46187d9be8033503721b7fbb6ac7fdb3edbca"
)
```

用 `bytes.fromhex` 而不是 `bytes([0x.., ...])`：后者在每次 `import` 时都要重建
一个几十万元素的列表，10 MB 的资源会非常慢。相邻字符串字面量由解析器拼接，
所以换行不影响结果。数组和摘要都用 4 个空格缩进，不混 tab。

## 压缩之后

同一个 104 字节的输入（8 行 `hello world!`）用
`--compress deflate -cbc <key>` 生成。压缩后数组只有 48 字节：
裸 DEFLATE 把 104 字节压到不到 32 字节，CBC 填充到 32，再加上 16 字节 IV。

注意注释块多了第一行，多了一个 `*_raw_len`，多了两个摘要。

### C —— `greet.h`

```c

 * generated by bin2source - do not edit
 * deflate : raw, level 9
 * AES256CBC (PKCS#7)

 * key     : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90

	"5f89212948aeae79b59c2f7427357f4ce55b513f433df4d4e1edcca8265a5bcc"

	"986d5732354521a9a4826d6872234c86a5d04fb2a1cd01381ca586ff392591f2"
```

### Go —— `greet.go`

```go
// Code generated by bin2source. DO NOT EDIT.

package main

// deflate : raw, level 9
```

## base64 文本模式

给了 `-b64` 时，数组不是字节列表，而是 base64 文本。文本以外的东西都没变：

- 注释块多一行 `base64  : RFC 4648 standard, padded`；
- 载荷常量的名字带 `_b64` 后缀（`data_b64` / `DataB64` / `DATA_B64`）；
- 长度常量仍然是**解码后**的字节数，不是文本长度；
- 三个摘要的含义完全不变，都按解码后的字节算。

顺序是固定的：压缩 → 加密 → base64。所以读回来的时候反过来：**先 base64
解码，再按下面「解码」一节的步骤走**。

同一个 5 字节输入 `\x01\x02\x03\x04\x05` 的载荷声明：

```c
static const char data_b64[] = (
	"AQIDBAU="
);
```

```go
const DataB64 = "AQIDBAU="
```

```rust
pub const DATA_B64: &str = "AQIDBAU=";
```

```python
DATA_B64 = (
    "AQIDBAU="
)
```

各语言的解码：

- Go：`base64.StdEncoding.DecodeString(DataB64)`，标准库。
- Python：`base64.b64decode(DATA_B64)`，标准库。
- C / C++：标准库没有 base64，附一个约 20 行的解码函数（`test/roundtrip.py`
  里回环测试跑的就是这一份）：

```c
static int b64val(char c) {
    if (c >= 'A' && c <= 'Z') return c - 'A';
    if (c >= 'a' && c <= 'z') return c - 'a' + 26;
    if (c >= '0' && c <= '9') return c - '0' + 52;
    if (c == '+') return 62;
    if (c == '/') return 63;
    return -1;
}

/* out must have room for the decoded size, which is data_len. */
static size_t b64decode(const char *in, unsigned char *out) {
    size_t n = 0;
    unsigned acc = 0, bits = 0;
    for (; *in; in++) {
        int v;
        if (*in == '=') break;
        v = b64val(*in);
        if (v < 0) continue;
        acc = ((acc << 6) | (unsigned)v) & 0xFFFFFFu;
        bits += 6;
        if (bits >= 8) {
            bits -= 8;
            out[n++] = (unsigned char)((acc >> bits) & 0xffu);
        }
    }
    return n;
}
```

- Rust：标准库也没有。可以用 `base64` crate（`STANDARD.decode(DATA_B64)`），
  也可以照上面那份逻辑手写约 30 行——`test/roundtrip.py` 为了不依赖 crate
  用的就是手写版，能跑就说明可行。

文本长度和字节长度不是一回事：文本是 4 字符装 3 字节，所以分配缓冲区要用
`data_len`，不要用 `strlen` 的结果。

## 解码

工具**不生成解码代码**，这里给出格式契约，自己按语言实现。

拿到数组后，**严格按下面的顺序**走，每一步都有对应的常量可以验：

```
0. 给了 -b64 时先 base64 解码 -> 得到下面的数组字节
1. 数组字面量         -> 比对 array_sha256       （不需要密钥）
2. 按注释里的算法解密  -> 比对 <codec>_sha256     （没有 --compress 就跳过）
3. 按 <wire> 解压     -> 比对 sha256             （没有 --compress 就跳过）
```

第 1 步放在最前面，是因为它在拿到密钥之前就能跑：立刻能分清"数组本身坏了"
和"解密有问题"，这两种故障的排查方向完全不同。

细节：

1. `(array[0:16])` —— 前 16 字节是 IV，剩下的才是密文
   `(comment only)` —— 整个数组都是密文，IV 从注释抄
2. 按注释里写的算法解密
3. 解压**之前**先比 `<codec>_sha256`：这一步能把"密钥错了"和"数据坏了"分开
4. 按注释里 `<wire>` 那个词解压：`raw` 用裸 inflate，`frame` 用 Zstandard 解码。
   去填充只跟加密模式有关，和压缩无关。

**CTR** 是流密码：明文长度 == 密文长度。
**CBC** 会填充：明文 1047 字节 → 密文 1056 字节（补到 16 的倍数），
去填充的规则是看最后一个字节 `n`，去掉末尾 `n` 个字节即可。
压缩是独立的一层，不关心上面的分块。

### Go（deflate 用标准库，zstd 要引一个包）

```go
key, _ := hex.DecodeString("a1b2...8f90")   // 64 个 hex 字符
block, _ := aes.NewCipher(key)
iv, ct := Greet[:16], Greet[16:]

// 1. 数组完整性，不需要密钥
if sum := sha256.Sum256(Greet); hex.EncodeToString(sum[:]) != GreetArraySha256 {
    log.Fatal("array is corrupt")
}

// 2. 解密
plain := make([]byte, len(ct))
cipher.NewCTR(block, iv).XORKeyStream(plain, ct)   // CTR
// CBC 则用：
// cipher.NewCBCDecrypter(block, iv).CryptBlocks(plain, ct)
// pad := int(plain[len(plain)-1]); plain = plain[:len(plain)-pad]

// 3. 解密结果必须先对上压缩输出的摘要
if sum := sha256.Sum256(plain); hex.EncodeToString(sum[:]) != GreetDeflateSha256 {
    log.Fatal("key or IV is wrong")
}

// 4. 解压，然后才是原始文件
var out []byte
if 注释里写的是 raw {          // deflate
    zr := flate.NewReader(bytes.NewReader(plain))
    out, err = io.ReadAll(zr)
} else {                      // zstd，需要 github.com/klauspost/compress/zstd
    zr, _ := zstd.NewReader(bytes.NewReader(plain))
    out, err = io.ReadAll(zr)
}
if err != nil {
    log.Fatal(err)
}
if sum := sha256.Sum256(out); hex.EncodeToString(sum[:]) != GreetSha256 {
    log.Fatal("decompression produced the wrong bytes")
}
// out 就是原始文件，长度应当等于 GreetRawLen
```

`deflate` 是标准库 `compress/flate`，零依赖。`zstd` 需要
`github.com/klauspost/compress/zstd`——Go 标准库里有一个 `internal/zstd`，但它是
internal 且只有解码器，引用不了。

### Python（deflate 用标准库，zstd 要装包）

```python
import hashlib, zlib
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

# 1. 数组完整性，不需要密钥
assert hashlib.sha256(GREET).hexdigest() == GREET_ARRAY_SHA256

# 2. 解密
key = bytes.fromhex("a1b2...8f90")
iv, ct = GREET[:16], GREET[16:]
d = Cipher(algorithms.AES(key), modes.CTR(iv)).decryptor()
plain = d.update(ct) + d.finalize()
# modes.CTR 换成 modes.CBC 之后手动去 PKCS#7

# 3. 比对压缩输出的摘要
assert hashlib.sha256(plain).hexdigest() == GREET_DEFLATE_SHA256

# 4. 解压
out = zlib.decompressobj(-15).decompress(plain)      # deflate: raw
# out = zstandard.ZstdDecompressor().decompress(plain)   # zstd: frame
assert hashlib.sha256(out).hexdigest() == GREET_SHA256
assert len(out) == GREET_RAW_LEN
```

`wbits=-15` 里的负号**不能省**。写成 `zlib.decompress(plain)`（正 wbits）
会去找那两字节 zlib 头，直接报错——这正是 `deflate : raw` 那行注释要提醒的事。

Zstandard 要 `pip install zstandard`（`zstandard.ZstdDecompressor`）。本工具
生成的 frame 一定带内容大小字段，所以 `ZstdDecompressor().decompress(payload)`
这类一次性调用可以直接用，不需要传 `max_output_size`，也不用绕流式接口。Python
3.14 起标准库自带 `compression.zstd`，但那是新东西，别指望它在老版本上。

### C / C++ / Rust

这三个语言没有标准库 AES，也没有标准库 DEFLATE 或 Zstandard，需要外部实现：

| | deflate（raw） | zstd（frame） |
| --- | --- | --- |
| C / C++ | zlib 的 `inflateInit2(&s, -15)`，别漏那个负号 | libzstd 的 `ZSTD_decompress` / `ZSTD_decompressStream` |
| Rust | `flate2` 的 `read::DeflateDecoder` | `zstd` crate，或纯 Rust 的 `ruzstd` |

AES 三家都一样：OpenSSL 的 `EVP_DecryptInit_ex`、mbedTLS、libsodium，或 Rust 的
RustCrypto（`aes` + `ctr` / `cbc`）。

C 的缓冲区要按 `data_raw_len` 分配，别按 `data_len`：后者是压缩后的长度。
zstd 还要留意一件 deflate 不用管的事：**frame 里声明了内容大小**，解码器据此
准备内存。本工具生成的 frame 全部是 single segment 形态（声明的窗口=内容大小），
所以解码端的内存开销只跟资源本身成正比，和 `--level` 无关——2 KB 的资源不会
被要求准备几 MB 的窗口。

格式契约就是上面那四条，任何符合标准的 AES / DEFLATE / Zstandard 实现都能解开——
回环测试里用 OpenSSL 解 Go 加的密、用 zlib 解 Go 压的流，验证的就是这一点。
